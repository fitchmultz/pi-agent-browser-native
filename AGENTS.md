# pi-agent-browser-native

Native `pi` integration of `agent-browser` as a `pi` tool.

## Product-specific guidance

- Do **not** bundle `agent-browser` in this project.
- Assume `agent-browser` is installed separately and available on `PATH`.
- Baseline docs and verification against the current recommended `agent-browser` release. Runtime support uses the stable minimum in `scripts/agent-browser-target.mjs` (currently 0.35.0) with no upper cap and no version-specific compatibility shims.
- Do **not** add backwards-compatibility shims for unsupported upstream versions.
- Keep the integration thin and close to upstream `agent-browser` behavior.
- Agent usability is the product boundary. Do not add wrapper-owned authorization or safety gates around upstream-supported commands, paths, sessions, state, restore, profiles, config, file access, launch arguments, or environment variables. Invoking `agent_browser` authorizes the requested upstream capability; pass it through and let upstream, the browser, and the operating system enforce their own contracts. Wrapper validation is for input shape, process integrity, lifecycle correctness, and truthful evidence—not for deciding what the agent or operator may do.
- The primary UX is the agent invoking the native tool directly, not a slash-command-heavy manual workflow.
- Do **not** overengineer or solve hypothetical problems that do not exist in observed behavior.
- Do **not** add a reusable named "browser recipe" runtime layer on top of browser code, advanced tools, or native batch without new dogfood evidence and an explicit design pass; the current no-adopt decision and revisit criteria live in [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md#no-reusable-recipe-layer-yet) and [`docs/SUPPORT_MATRIX.md`](docs/SUPPORT_MATRIX.md).
- Require Node 24.21.0+ and Pi 1.0.0+ for this contract; retain locked development dependencies as reproducible snapshots, keep optional runtime peers wildcard, and qualify the latest stable official Pi and latest maintained fork main independently. Resolve version/commit once per workflow run and retain exact SDK/CLI evidence; never use the support floor or locked snapshot as a validation target. Do not activate the Pi-1.0 package on pre-1.0 sessions before the coordinated runtime cutover.
- Thoroughly check official `pi` docs/examples/source behavior before inventing bespoke integration patterns. Prefer an official `pi` mechanism whenever one exists.
- Prioritize the global install path first. Most users will install this extension globally, not as a project-local extension.
- Keep the local extension-side documentation good enough that an agent can use the tool without relying on direct `agent-browser` binary help; when upstream `agent-browser` changes, update the repo-readable command reference, prompt guidance, README/docs, and any relevant tests in the same work.
- Work in an isolated worktree and preserve unrelated user and agent changes; other operators may be working in this repository.
- Clean up scratch files, temp artifacts, browser sessions, tmux sessions, and other side effects created by this task or verified as task-owned. Preserve unrelated resources, explicit user artifacts, Pi transcripts, and subagent records; investigate unknown ownership before cleanup.

## Documentation placement

- Put user-facing product docs in `README.md` and `docs/`.
- Put agent-specific operational notes, workflows, and testing procedures in this `AGENTS.md`.
- Write documents as complete documents, not iterative logs, unless the document is explicitly meant to be iterative such as `CHANGELOG.md`.

## Code quality, maintainability, and verification

Use the pinned repository runtime, npm, lockfile, and existing verification
workflow. [`docs/CODE_QUALITY.md`](docs/CODE_QUALITY.md) owns commands, coverage,
the reproducible checker correction, and exception contracts.

- Correctness, long-term maintainability, and reliable enforcement are equal
  requirements. Keep production complexity, size, readonly, and safety controls;
  a finding need not identify an existing runtime bug to justify fixing it.
- A substantial refactor must make responsibilities, state ownership, asynchronous
  phases, failure behavior, and cleanup clearer. Keep internal APIs private;
  avoid forwarding chains, arbitrary file splits, indiscriminate shared contexts,
  and speculative frameworks. A useful single-use helper is not a problem.
- Additional relaxations require concrete diagnostic/contract evidence and explicit
  approval. Existing authorized exception classes still require their demonstrated
  conditions; substantial work or diagnostic counts are not grounds to relax them.
- Run `npm run quality` on the integrated revision; CI additionally proves real
  failure propagation with `npm run quality:mutations`.
- Use `npm run lint`, `lint:agent`, and reviewed `lint:fix` for identical coverage;
  Oxfmt owns `format` and non-modifying `format:check`.
- TypeScript and checked JavaScript retain semantic lint and compiler gates.
  Other maintained JavaScript retains syntactic lint, formatting, and tests.
  Effective compiler membership/settings and real per-file directives determine
  scope. Regenerate the exact final root JS override with
  `npm run quality:scope -- --write` only after intentional scope/tool changes.
- CLI and editor LSP must use `scripts/oxlint.mjs` and its verified corrected
  backend; do not substitute a global/raw checker or broad allowance.
- Verify declaration-qualified native/SDK/safe-call exceptions using positive and
  negative origin-isolation probes. An approved call passing is insufficient.
  Keep floating-Promise checks strict and fix matcher defects rather than
  disguising/discarding promises.
- Preserve accurate contracts and runtime behavior. Replace unsafe types with
  validation, narrowing, and sound relationships; prefer contextual inference
  where useful while keeping exported contracts explicit.
- Preserve asynchronous ordering, cancellation/deletion guards, error identity,
  transactional guarantees, argument presence, and cleanup ownership.
- Use only documented, narrow semantic exceptions with adjacent reasons and
  supporting boundary evidence. `quality:policy` parses actual comments and
  inventories exceptions; unused disables remain errors.
- Keep cohesive lifecycle tests together. Tests retain branching/parameter limits
  but not size/statement limits. Actual `node:test` safety checks run through
  Oxlint; do not configure Vitest rules as a substitute.
- Correct invalid fixture initialization without weakening intended assertions.
  Report fixture fixes separately from production runtime bugs.
- Refactor production modules along real responsibilities; review autofixes and
  retain meaningful coverage. Fix generators rather than generated doc blocks.
- Report executed commands, coverage, exception verification, checker corrections,
  and remaining limitations accurately. Separate formatting, configuration changes,
  maintainability improvements, checker fixes, fixture repairs, and runtime bugs.

## Upstream capability baseline and command reference

When upstream `agent-browser` changes version or help text, keep three layers aligned:

1. **Canonical metadata** — `scripts/agent-browser-target.mjs` defines the recommended upstream version and minimum supported stable version, while `scripts/agent-browser-capability-baseline.mjs` defines which `agent-browser <args>` help outputs are sampled for drift checks, and which literal tokens must appear in upstream help and in human-written sections of `docs/COMMAND_REFERENCE.md` (grouped as inventory sections). Nothing in this file shells out to `agent-browser`; rebaselining is an explicit maintainer edit after comparing real `--help` output from the installed binary.

2. **Human command guide** — `docs/COMMAND_REFERENCE.md` holds the readable workflows, examples, and constraints. Outside the two HTML-comment bounded generated regions (`upstream-baseline`, `capability-token-baseline`), edits are normal prose. Every human-authored token listed in the baseline must appear somewhere in the doc body so agents searching the repo see real usage, not only generated lists.

3. **Generated blocks** — The baseline checker renders versioned boilerplate into `docs/COMMAND_REFERENCE.md`. After changing the baseline metadata, run `npm run docs -- command-reference write`. Do not hand-edit inside the `<!-- agent-browser-capability-baseline:start ... -->` / `<!-- ...:end ... -->` markers.

Release-readiness checklist: [`docs/SUPPORT_MATRIX.md`](docs/SUPPORT_MATRIX.md) maps each baseline inventory section to human docs, wrapper/runtime behavior, tests, and verification gates. Refresh it when rebaselining upstream.

Verification stack:

- `npm run typecheck` — runs the same `tsc --noEmit` step as the default verify gate (`scripts/project.mjs` `verify typecheck`) without playbook drift, unit tests, or live upstream command-reference sampling; use for fast TypeScript iteration.
- `npm run docs` (or `npm run docs -- command-reference check`) — generated blocks match `agent-browser-capability-baseline.mjs`.
- `npm run verify -- command-reference` — the above plus live `agent-browser --version` and help sampling against the same baseline (requires the targeted upstream on `PATH`).
- Unit coverage for the verifier and block renderer lives in `test/verify-command-reference.test.ts`.

**npm verification facade:** `npm run verify` and `npm run docs` delegate to [`scripts/project.mjs`](scripts/project.mjs) (`verifySteps` / `docsSteps`). ### Runtime planning (`extensions/agent-browser/lib/runtime.ts`)

Native configured session/namespace selection and automatic root-Pi named-session fallback are adapted at `lib/orchestration/native-session-defaults.ts` before the existing caller-owned planning/queue path. Root identity is `PI_SUBAGENT_ROOT_SESSION_ID` for delegated children and the current Pi ID otherwise; never infer it from cwd or ordinary fork ancestry. Root bootstrap uses global/override package profile names with policy `always` and per-root native restore, scoped across every helper and matching root-name follow-up; paths/project-only guidance remain advisory and unrelated explicit sessions remain untouched. Read only identity fields and use sessionless native config validation rather than duplicating its schema; carry explicit config/idle overrides through the async-local process environment. Keep managed/fresh and Electron ownership separate from root-group caller ownership; code follows its parent-selected ordinary browser. `test/agent-browser.shared-defaults.test.ts` covers caller ownership, precedence, helpers and the opt-in local-profile/code boundary.

This module is **pre-spawn planning only**: it validates raw `args`, derives implicit or fresh managed session names, classifies browser prompts, redacts invocation text, and builds `effectiveArgs` for the upstream binary. It does not spawn processes or touch the filesystem.

- **`buildExecutionPlan`** — Injects `--json`, optionally injects extension-managed `--session` for `sessionMode: "auto"`, applies the site-specific headless `--user-agent` workaround when eligible by argv and upstream launch environment, retains it for the current wrapper-managed session while preparation restores per-owned-session compatibility for off-current targets, and returns `validationError` plus a structured `recoveryHint` when launch-scoped flags would be ignored on an already-active implicit session (surfaced to Pi as `details.sessionRecoveryHint` by `orchestration/browser-run/prepare-failure.ts`).
- **Command discovery** — `extensions/agent-browser/lib/argv-descriptor.ts` and `extensions/agent-browser/lib/argv-grammar.ts` own `findCommandStartIndex`, `VALUE_FLAGS`, `parseArgvDescriptor`, and `parseCommandInfo`; `buildExecutionPlan` consumes the descriptor instead of re-parsing tokens. `findCommandStartIndex` walks leading tokens using `VALUE_FLAGS` and `GLOBAL_BOOLEAN_FLAGS_WITH_OPTIONAL_VALUES` so known value-taking flags ahead of the upstream command word consume their values before the command is identified. `stripUpstreamGlobalFlags` / `extractUpstreamCommandTokens` then mirror upstream 0.34.0 `clean_args` across the full command tail for semantic, lifecycle, presentation, and protected-path parsing while `extractCommandTokens` remains the raw-slice helper for argv reconstruction. Artifact consumers clean globals only on outer CLI argv; native `batch` rows go directly to upstream `parse_command`, so global-looking row tokens remain literal operands. Missing-value prevalidation is narrower: `PREVALIDATED_VALUE_FLAGS` is global-value-only so command-scoped flags or literal free text such as `fill #field --password` are left to upstream parsing instead of being rejected by wrapper heuristics. A smaller set of global booleans may be followed by an optional `true`/`false` literal; when present, that literal is consumed before command discovery continues, and repeated boolean flags follow upstream's last-occurrence-wins semantics with only a separated exact lowercase `false` disabling the final recognized occurrence; unsupported equals tokens such as `--auto-connect=false` are rejected before dispatch instead of overriding an earlier bare flag. When upstream adds new globals that take a separate argv value before the subcommand, extend command discovery and prevalidation; for new command-specific flags, extend command discovery/redaction only when wrapper features need to understand them.
- **Launch-scoped flags** — `extensions/agent-browser/lib/launch-scoped-flags.ts` owns `LAUNCH_SCOPED_FLAG_DEFINITIONS` (currently `--allowed-domains`, `--auto-connect`, `--namespace`, `--cdp`, `--enable`, `--engine`, `--executable-path`, `--webgpu`, `--no-webmcp`, `--init-script`, `--idle-timeout`, `--args`, `--user-agent`, `--headed`, `--device`, `--profile`, `--provider`, `-p`, `--session-name`, `--restore`, `--restore-save`, restore check flags, and `--state`); `getStartupScopedFlags` mirrors that metadata. `--auto-connect` counts only when enabled (bare or `true`); `--state` after a `wait` command is treated as a wait predicate, not launch state, so it does not force `sessionMode: "fresh"` during implicit reuse. Preparation also rejects launch-scoped flags for off-current wrapper-owned sessions after daemon inspection proves the target active. Keep `--allowed-domains` fresh-launch-only: upstream owns network/worker/popup/WebRTC containment and incompatible-mode rejection; do not add wrapper enforcement.
- **Tab-correction signal** — `hasLaunchScopedTabCorrectionFlag` is a subset (`--profile`, `--session-name`, `--state`) for post-open tab re-selection when restored tabs steal focus; it intentionally excludes `--cdp`, `--auto-connect`, and provider selection flags (`-p`, `--provider`, `--device`).
- **Process identity probes** — `extensions/agent-browser/lib/process-identity.ts` centralizes POSIX `ps` and native-Windows PowerShell command construction for PID-reuse-safe daemon-policy locks and secure-temp stale-root cleanup.
- **Upstream subprocess environment** — `extensions/agent-browser/lib/process.ts` passes through the parent environment so user-approved provider credentials and other runtime variables reach upstream, then applies wrapper overrides such as the managed socket directory, managed-session idle timeout, clamped default operation timeout, canonical owned-session namespace (including empty default), and managed-session restore env from the pure `getManagedSessionRestoreEnv` resolver in `extensions/agent-browser/lib/managed-session-restore.ts`; on POSIX, the selected socket directory must be absolute, current-uid-owned mode `0700`, under trusted ancestry, and free of symlink, foreign-owner, or special planted entries, with pre-existing unsafe modes rejected rather than repaired and validation repeated before spawn; `commitManagedSessionRestoreSuppression` records a restore-disabled identity only after an owned-context child emits `spawn` on POSIX; the Windows `cross-spawn` path commits after process completion unless the spawner reports an error such as `ENOENT`. Every subprocess targeting a wrapper-owned session—including helper probes such as fresh snapshots, tab lists, and navigation summaries—must receive the same implicit `AGENT_BROWSER_IDLE_TIMEOUT_MS`; caller-owned sessions retain native idle policy (including an unset value), and per-call idle/config overrides must reach their helpers; compatible non-close subprocesses must also receive the same restore decision for a given managed session, while close omits the wrapper's automatic key without changing caller environment. Wrapper-owned headed launches default `AGENT_BROWSER_AUTOSAVE_INTERVAL_MS` to `0` unless the caller set it because upstream 0.33.2's periodic multi-origin collector opens visible temporary targets and holds the daemon lock; the owned managed-session context retains the effective launch-time interval across every helper and follow-up subprocess, including transcript reload/resume, so daemon configuration stays stable; any explicit change in either direction must fail until close plus a fresh launch. Native close still saves, but direct window close can lose newer state because headed browsers are exempt from idle shutdown. Upstream can otherwise restart the background browser between calls, discard the active tab, invalidate fresh refs, or switch restore keys mid-session. Keep model-facing output redacted, but do not drop execution-path secrets merely because their names are not known to this wrapper.
- **Attached browser continuity** — successful `connect`, `--cdp`, enabled `--auto-connect`, matching environment launches, and wrapper Electron attachments are branch-visible session state. 2. Keep `docs/COMMAND_REFERENCE.md` human prose aligned with the baseline: every inventory token the baseline expects in the doc must appear **outside** the two generated regions (`upstream-baseline`, `capability-token-baseline`). `scripts/verify-command-reference.mjs` strips those generated blocks and fails if any required token is missing from the remaining Markdown.
3. Regenerate the HTML-comment bounded blocks with `npm run docs -- command-reference write`. If you also changed playbook source in `extensions/agent-browser/lib/playbook.ts`, refresh every generated doc fragment in one shot with `npm run docs -- write` (runs playbook drift rewrite plus command-reference rewrite).
4. Before committing, run `npm run docs` (or `npm run docs -- command-reference check`) so checked-in blocks cannot drift from the baseline file.
5. When the targeted `agent-browser` is available on `PATH`, run `npm run verify -- command-reference`. It enforces `agent-browser --version` against the baseline, re-samples each `helpCommands` invocation for expected upstream tokens, and repeats the human-token scan against `docs/COMMAND_REFERENCE.md`.

## Preferred testing workflow

Use an end-to-end interactive `pi` run inside `tmux`.

### Rules

- Use two distinct validation modes and do not mix their assumptions:
  - **Checkout-only extension mode:** launch `pi --approve --no-extensions -e .` from this trusted repository root. Automatic extension loading is disabled, but Pi settings, configured package resolution, and other resource types remain active. For isolated test settings, use temporary `HOME` and `PI_CODING_AGENT_DIR` directories with `PI_OFFLINE=1`; provide only the model credentials the smoke needs. Restart Pi after extension edits rather than using `/reload` as this mode's validation target. Omit `--approve` only when testing Project Trust.
  - **Configured-source lifecycle mode:** run `npm run verify -- lifecycle` before every publish for deterministic `/reload`, exact `--session-id` relaunch, managed-session continuity, persisted-spill, and native returned-failure regression coverage (see [`docs/RELEASE.md`](docs/RELEASE.md#pre-release-checks)). Focused extension harness tests cover Pi `session_tree` branch rehydration and cleanup ownership. The lifecycle harness defaults to Pi model `zai/glm-5.2`, **180000 ms** per-step waits in `scripts/verify-lifecycle.mjs`, and accepts `--model <id>` / `--timeout-ms <ms>` passthrough. The npm verification facade removes npm-injected `node_modules/.bin` entries from the lifecycle child `PATH` so tmux launches the maintainer's host Pi instead of a development dependency binary (for example `npm run verify -- lifecycle --model openai-codex/gpt-5.5:minimal`). During development you can also configure exactly one active source for this extension in Pi settings and launch plain `pi` for manual validation of reload/relaunch behaviors because `/reload` exercises auto-discovered/configured resources.
- For code changes, a checkout-only `pi --approve --no-extensions -e .` smoke session is a pre-commit requirement; whoever made the changes should validate unpublished checkout behavior there before commit/push (a published install alone is not a substitute).
- When validating real extension behavior, run real Pi/model sessions with the target model, for example `pi --approve --model zai/glm-5.2:high --no-extensions -e ./extensions/agent-browser/index.ts`. Do **not** add `--no-session` to these checks: preserve the Pi JSONL transcript so tool-result semantics, model-visible content, and follow-up behavior can be reviewed. Prefer a disposable `--session-dir <temp-dir>` when isolation is needed, then inspect and retain Pi JSONL evidence; clean only disposable browser and fixture files.
- Before every release, run real-site interactive dogfood in `tmux` with `pi --approve --no-extensions -e .` and the native `agent_browser` tool. Cover at least one simple static site and one real docs/product site, include advanced QA, code, or native batch when those surfaces changed, verify refs/navigation/artifacts/session cleanup from the transcript, close sessions, remove screenshots/temp files, and record the outcome in release evidence. Automated localhost, fake-upstream, and package smoke gates are not a substitute for this live-site tmux dogfood. When a smoke prompt is meant to validate this extension rather than external dogfood/QA skill behavior, add `--no-skills` and use the bounded release-smoke wording in [`docs/RELEASE.md`](docs/RELEASE.md#public-sauce-demo-checkout-smoke-prompt); run skill-enabled dogfood separately only when skill routing itself is under test. When dashboard, diagnostic, artifact, recording, scroll, or combobox behavior changed, use the public Grafana checklist in [`docs/RELEASE.md`](docs/RELEASE.md#public-grafana-stress-checklist); do not commit private dogfood/VFR skills or run artifacts.
- For installed-package validation after publish: update the real installed package, then exercise it with only the published package active—either temporarily disable/remove the checkout path and run plain `pi` for lifecycle validation, or use an ephemeral extension-only smoke run like `pi --no-extensions -e npm:pi-agent-browser-native` (with the isolated settings environment above when needed).
- Use `tmux` via bash commands.
- Do **not** use the pi interactive shell extension for this workflow.
- Drive `pi` like a real user by sending prompts normally.
- The extension blocks direct `agent-browser` bash calls by default to push agents toward the native tool. During this package's own development, the guard is bypassed when the session cwd is this package root (`package.json` name `pi-agent-browser-native`) or when `PI_AGENT_BROWSER_ALLOW_DIRECT_BASH=1` is set, so upstream CLI behavior can be debugged directly.
- After extension changes in configured-source lifecycle mode, `/reload` is the minimum, but a full close-and-relaunch of `pi` is preferred for higher confidence. The automated `npm run verify -- lifecycle` harness creates an isolated `PI_CODING_AGENT_DIR`, configures a temporary package source, drives `pi --approve` in `tmux` with an exact `--session-id`, uses a deterministic fake upstream `agent-browser`, checks `/reload` plus restart with the same session id, and captures transcript artifacts on failure.
- If continuing the same conversation after restart, use `/resume` or an explicit session path/id.
- Resumed/exact-session sessions should reflect the updated configured extension source after restart.

### Practical tmux notes

- Prefer `tmux send-keys ... Enter` for prompt submission. Collapse multi-line smoke prompts to one line before `send-keys`, or use Pi's external editor / tmux extended-keys path; raw pasted newlines become separate queued user messages.
- Capture larger pane ranges when debugging: `tmux capture-pane -p -S -300 -t <session>:0.0`.
- Clean up tmux sessions after testing.
- Before ending a turn, sweep for and remove repo-local scratch files, project-scoped temp artifacts, and lingering browser sessions created during the work unless the user explicitly asked to keep them.
- Do not overfit testing to `example.com`; use it for smoke checks only, then validate against additional realistic pages and flows. The lifecycle harness intentionally uses a fake upstream browser for deterministic lifecycle assertions and does not replace occasional real-browser manual smoke testing before release.
- Prefer **tmux** over `pi -p` for real-browser checkout and release smokes; print mode may hang without a TTY. Use npm 12 when touching `package-lock.json` (`packageManager` in `package.json`), and never commit WorkOS or other private-registry URLs in that lockfile. After real-browser runs, close sessions and sweep lingering browser/tmux temp artifacts. Maintainer environment pitfalls (Pi/npm version skew, lifecycle `/reload` timing, automated pane matchers) are documented in [`docs/RELEASE.md`](docs/RELEASE.md#environment-and-automation-pitfalls).
